# Report Version And Deploy Verification

## Goal

Display report version `v1.2.12` in the personalized-report heading and make every new deployable commit prove its version, deployment identity, and JS/CSS cache behavior in production.

## Version Contract

`package.json` is the single source of truth for the report version. Set it to `1.2.12` and render the heading as:

```text
Relatório personalizado · <data> · v1.2.12
```

The English heading follows the same structure. Source code must not duplicate the version literal.

Every new commit deployed by a push to `master` or `main` must use a version different from the currently published production version. A manual workflow re-run of the same commit and version remains valid for recovery or cache refresh.

## Deployment Manifest

The build produces `/deployment.json` containing:

- `reportVersion`: semantic version from `package.json`;
- `commitSha`: exact Git commit deployed;
- `builtAt`: UTC ISO timestamp generated by CI.

The manifest is deployment metadata only. It contains no respondent data and is not part of report JSON persistence.

## Cache Policy

Static HTML and `deployment.json` must be revalidated on every request with `Cache-Control: no-cache, no-store, must-revalidate`. Hashed files under `/_next/static/` use `Cache-Control: public, max-age=31536000, immutable` because any JS/CSS content change produces a different asset URL.

The PHP report endpoint retains its existing `Cache-Control: no-store` response. Existing saved reports and their payload schema remain unchanged.

## Deployment Verification

Before a push-triggered publish, CI reads the production manifest. If production already reports the candidate version under a different commit, the job fails and requires a version bump. Workflow-dispatch recovery runs may redeploy the same version.

After atomic publication, CI fetches production with cache-busting query parameters and verifies:

1. production returns HTTP 200;
2. `deployment.json` matches the expected version and commit SHA;
3. production HTML references JS/CSS files from the deployed `_next/static` directory;
4. every referenced JS/CSS URL returns HTTP 200;
5. HTML and manifest use the no-cache policy;
6. hashed JS/CSS use the immutable cache policy;
7. the heading copy and version exist in the published JavaScript;
8. the report-data directory remains mounted and writable without reading or modifying respondent JSON.

## Documentation

Add root `AGENTS.md` with mandatory repository rules and `docs/RELEASE.md` with the operator checklist. They must require:

- bumping `package.json` for each new deployable commit;
- updating version-sensitive tests;
- running the full PHP 8.2 test suite and production build;
- waiting for the deployment workflow to succeed;
- checking the production manifest and asset cache headers;
- never deleting, synchronizing, or exposing saved report JSON files.

Historical specifications and plans remain historical records and are not rewritten.

## Testing

- Unit-test report-heading formatting against the package version.
- Unit-test deployment-manifest generation and validation helpers.
- Run all TypeScript and PHP integration tests.
- Run a clean production build and verify generated HTML, manifest, and asset references locally.
- Deploy through the guarded workflow and repeat the manifest/header/asset checks against production.
